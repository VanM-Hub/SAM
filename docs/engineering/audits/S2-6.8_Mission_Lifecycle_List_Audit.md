## 1. Lifecycle AKTUAL (source aktual)

Alur nyata dari source `src/sam/application/ux/*`:

```
operation detection (_interpret, servis L826+)
      ↓ _interpret mengembalikan (operation, target, understood, planned, ...)
MissionRequest (mission_request.py) — DTO immutable
      ↓ MissionUXService.submit() (service L360+)
MissionPlan (plan.py) — ViewModel rencana
      ↓ approval? (approval.py) + state
UxMissionState (state.py) — ViewModel state observable tunggal
      ↓ _persist() / _persist_entities()
MissionStore (JSON tunggal) + PersistenceUnit (misi/eksekusi/approval/audit/evidence/idem) [repositori.py]
      ↓ /ux/state (route L211) — UI membaca state TUNGGAL
```

### Status lifecycle yang tersedia SAAT INI

| Status | Di mana | Kapan dipakai |
|---|---|---|
| **DRAFT** | `MissionRequestStatus`, `MissionPlanStatus`, `UxStateStatus` → TIDAK ada | Request DRAFT: tak dipakai di mana pun. Plan DRAFT: dipakai (service L434) utk **read-only mission** |
| RECEIVED | `MissionRequestStatus` | Request terdefinisi, jarang dipakai |
| UNDERSTOOD | `UxStateStatus`, `MissionRequestStatus` | Semua mission pasca submit non-approval |
| WAITING_APPROVAL | `UxStateStatus` | Mission mutating yang menunggu user |
| APPROVED / REJECTED / RUNNING / COMPLETED / FAILED / BLOCKED / RETRYABLE | `UxStateStatus` | Jalur approval+eksekusi |

### Fakta kunci dari source

1. **`MissionRequestStatus.DRAFT` TIDAK pernah dipakai** — hanya didefinisikan di `mission_request.py`.
2. **`MissionPlanStatus.DRAFT` DIPAKAI** (service L434): read-only mission (approval_required=False) diberi status `DRAFT`, bukan `PENDING_APPROVAL`. Komentar eksplisit: *"DRAFT = Mission dibentuk tapi tidak menunggu approval (candidate/read-only)"*. → **Ini grounding DRAFT yang relevan.**
3. **`UxStateStatus` TIDAK punya `draft`/`proposed`** — mulai dari `NONE`/`RECEIVED`. UI membaca `UxMissionState.status`; state read-only = `understood`.
4. **State yang UI lihat adalah SATU state global** (`get_state()` → `self._state`, service L852). Route `/ux/state` mengembalikan ViewModel tunggal.
5. **`_recover_from_repository` hanya pulih ke mission TERAKHIR** (`missions[-1]`, service L331) — service tunggal tidak "menyimpan daftar aktif", hanya state terakhir.
6. **`MissionRegistry`/`MultiMissionService` ADA & teruji (M12-012)** — keyed `(tenant, mission_id, execution_id)`, bisa `list_keys()`, `mission_count()`, isolasi penuh. **TAPI TIDAK di-wire ke route `/ux/*`** dan tidak dipakai jalur produksi. Route memakai `MissionUXService()` tunggal (routes/ux.py L95).
7. **Conversation** memanggil `MissionUXService.submit()` (SATU pintu, conversation.py L369), lalu **TIDAK menyimpan link mission ke Message** (keputusan S2-3: conversation bukan "persistence kedua"). Assistant message `evidence_refs` hanya menampung url/target evidence — **tanpa mission_id/request_id**.
8. **Tidak ada jalur "mission draft terbentuk tapi belum di-submit"** — mission lahir **hanya** saat `submit()` dipanggil. Tidak ada entity "proposed mission" yang berdiri sendiri sebelum submit.

## 2. Lifecycle yang DIBUTUHKAN UI (Mission List sebagai Layer 2)

Empat tahap yang diminta Van untuk direpresentasikan:

```
Proposed/Draft Mission → selected Mission → prepared Mission → approval → execution
```

Artinya Mission List perlu bisa **menampilkan SEMUA mission yang "sedang ada"** (terutama yang masih draft/proposed dan yang menunggu approval), lalu user **memilih** satu untuk masuk ke detail.

| Tahap UI | Yang ditampilkan | State yang cocok saat ini |
|---|---|---|
| **Draft/Proposed Mission** (list) | Kumpulan mission yang belum diputus: yang baru dibentuk (read-only candidate) + yang menunggu approval | Perlu enumerasi **banyak** mission |
| **Selected Mission** | Saat user klik satu mission di list → fokus ke mission itu | `get_state()` per mission terpilih |
| **Prepared Mission** | what_sam_understood + planned_steps + approval_required | `MissionPlan` (sudah ada) |
| **Approval** | Approve/Reject | `ApprovalRequest` + `decide()` (sudah ada) |
| **Execution** | Running → Complete/Failed | `decide()` → `run_mission` (sudah ada) |

## 4. Gap

### GAP-1 (KRITIS — struktural): Enumerasi mission aktif TIDAK di-expose ke UI/jalur route
- Kapabilitas `list_missions()`/`list_keys()` **ada**, tetapi route saat ini hanya mengekspos **SATU state** (`/ux/state` → `service.get_state()` tunggal L95 wiring).
- UI TIDAK bisa menampilkan banyak mission karena adapter route tidak memakai `MultiMissionService`.
- **Ini GAP UTAMA** — bukan kekurangan model/state, melainkan kekurangan *wiring/exposure*.

### GAP-2 (KRITIS — semantik): Tidak ada status "draft/proposed" pada level STATE yang UI baca
- `UxStateStatus` tidak punya `draft`. Read-only mission statusnya `understood`, mutating `waiting_approval`.
- Tapi **`MissionPlanStatus.DRAFT` ada** — hanya saja level itu (Plan) tidak di-ekspos langsung sebagai "status list mission" oleh UI route (UI membaca `UxMissionState.status`, bukan `MissionPlan.status`).
- Pertanyaan Van "apakah DRAFT cocok untuk tahap proposed": **`MissionPlanStatus.DRAFT` secara semantik TEPAT** untuk "dibentuk, belum menunggu approval" (read-only candidate). Namun ia tidak dipakai untuk mission mutating (yang memakai PENDING_APPROVAL), dan tidak terekspos sebagai field list.

### GAP-3 (SEMANTIK — kosakata UI): Tidak ada `mission_id` yang stabil & konsisten untuk ditampilkan di list
- Mission punya `mission_id` di observability (bentuk `mission-<hex>`), request_id, plan_id, execution_id — **empat ID berbeda** di level berbeda.
- Mission List butuh **satu identitas tampilan** yang stabil per "card". Saat ini `mission_id` (observability) adalah kandidat, tapi service tunggal tidak menyimpan daftar mission_id aktif.

### GAP-4 (minor): Read-only mission "draft" tidak bisa lanjut ke eksekusi
- `decide()` (service L474) **menolak read-only mission** (REJECTED, "invalid capability"). Jadi mission read-only **berakhir sebagai draft/understood** — tidak ada jalur eksekusi berikutnya.
- Untuk Mission List layer 2, ini bukan masalah: draft read-only cukup **ditampilkan** sebagai "proposed", tidak perlu eksekusi. (Konsisten dgn verdict Van: read-only tidak di-execute di milestone ini.)

## 5. Apakah gap bisa diselesaikan dengan EXISTING state/model? → **YA, tanpa konsep domain baru**

- **GAP-1** → diselesaikan dengan **me-wire `MultiMissionService` (sudah ada & teruji) ke jalur baru** yang me-list mission: `registry().list_keys()` → ambil `get_state()` per key. **TIDAK membuat mission baru / state machine baru** — memakai `MissionRegistry` yang sudah ada.
- **GAP-2** → `MissionPlanStatus.DRAFT` **sudah tepat secara semantik** untuk "proposed/draft mission". Tinggal **memproyeksikan** DRAFT dari level Plan ke level list (bukan membuat status baru). Untuk mission mutating, DRAFT juga bisa diperlakukan sebagai "proposed" di list sebelum approval (state-nya `waiting_approval`).
- **GAP-3** → pakai `mission_id` (observability, `mission-<hex>`) sebagai identitas list; sudah disimpan di registry key. Tidak perlu ID baru.
- **GAP-4** → bukan blocker untuk Mission List (draft read-only = tampilan "proposed", tidak perlu jalur eksekusi).

**Kesimpulan gap:** Tidak ada kebutuhan **state machine baru**. `MissionRegistry` + `MissionPlanStatus.DRAFT` + `UxMissionState` sudah cukup. Yang kurang **hanya wiring/exposure**: (a) expose list missions dari `MultiMissionService`, (b) proyeksikan `DRAFT`/status ke level list. Keduanya memakai entity & model yang sudah ada (per AD-ENG-004: "JANGAN minta izin, buktikan", dan prinsip "capability over implementation").

## 6. Proposal BOUNDARY untuk Mission List (Layer 2)

Berdasarkan audit, boundary yang diusulkan (belum diimplementasi — hanya rekomendasi arsitektur):

```
Conversation (L1)  --mission terbentuk-->  MultiMissionService (berisi MissionUXService otonom per mission)
                                              │
                              /ux/missions (BARU — list) ← registry().list_keys() → get_state() per key
                              │                 (semua: draft/read-only + waiting_approval)
                              ▼
                    Mission Detail (single) ← /ux/missions/{mission_id}/state
                              │
                              ▼
                    Approval (/ux/decide reuse) → Execution (reuse)
```

**Aturan boundary (agar tidak menciptakan konsep domain baru):**
1. **Mission TETAP lahir hanya via `submit()`** (semantic operation → capability). Mission List HANYA **membaca** registry — tidak membuat mission.
2. **Mission List = proyeksi read-only** dari `MissionRegistry` (source of truth = per-entity repo). **Bukan persistence kedua, bukan state machine baru.**
3. **Satu asumsi ID**: `mission_id` (observability) = identitas tampilan. `request_id`/`plan_id`/`execution_id` tetap internal (tidak ditampilkan sebagai identitas list).
4. **Status yang ditampilkan di list** dipetakan dari existing state (tanpa enum baru):
   - `read-only` (operation environment.*) → tampil sebagai **"Proposed/Draft"** (grounding `MissionPlanStatus.DRAFT`)
   - `waiting_approval` → tampil sebagai **"Menunggu Persetujuan"**
   - `running`/`completed`/`failed`/`blocked`/`rejected` → status existing
5. **Approval & Eksekusi TIDAK berubah** — tetap lewat `decide()` canonical. Mission List hanya pintu masuk ke detail mission yang sudah ada.
6. **Isolasi** (tenant/mission) tetap dijamin `MissionRegistry` (M12-012). List per tenant via `list_keys(tenant=...)`.
7. **TIDAK menambah field ke model universal** (Message/Conversation) — tidak ada assosiasi mission di conversation (konsisten S2-3).

**Pertanyaan yang perlu keputusan Van (setelah audit):**
- A. Apakah Mission List di-*wire* via `MultiMissionService` (jalur yang sudah ada) sebagai endpoint `/ux/missions`, ATAU cukup memperluas `MissionUXService` tunggal agar bisa me-list? (Saya rekomendasi: `MultiMissionService` — sudah teruji isolasi.)
- B. Apakah mission yang lahir dari conversation (`/ux/conversation/message`) juga harus masuk Mission List? Saat ini conversation mission TIDAK menyimpan link ke repo conversation (S2-3), tapi state mission-nya ada di `MissionUXService`/repo. Perlu keputusan apakah list di-scope ke semua mission service atau hanya conversation utama.
